# Product scope — v1 frozen

目标：让面试官通过一个可解释、可维护的企业应用，观察 Java 事务/权限/数据库能力与 Python AI 应用能力。假设单企业、最多约 100 个演示用户、100 个知识库、10,000 个 chunk；这些是设计容量预算，不是已验证性能承诺。

## 必须交付的垂直流程

| 用户 | 业务任务 | v1 完成标准 |
| --- | --- | --- |
| Employee | 查制度、查看来源、提交并跟踪自己的工单 | 有权限的引用可打开；找不到资料时拒答；无需 AI 可创建、评论、取消自己的开放工单 |
| Support Agent | 处理本部门工单 | 列表、认领/分配、进度和解决说明可追踪 |
| Knowledge Manager | 管理负责知识库 | 上传、查看处理失败、重试、发布新版本、归档；旧版本证据不被覆盖 |
| Administrator | 管理账号、部门、角色、知识库授权、审计 | 停用/撤权实时影响新请求；系统级变更可追踪 |

首版功能：登录/登出/刷新、RBAC+资源范围、知识库与成员授权、文件及版本、异步解析与状态、检索与带引用问答、工单/评论/分配/状态历史、七个有限 AI 工具、人工确认、审计与基础管理视图。管理员初始化账号使用本地一次性命令，密码从环境读取；不提供公开注册。

## 范围约束

- 单组织；部门为权限范围的一部分，不是多租户；每个用户仅有一个主部门，可有多个角色。
- 工单归属部门创建时取提交者当前部门，此后不自动随用户调岗变化；v1 不做跨部门转派。
- 知识库采用显式用户成员授权 `READER` / `MANAGER`。所有业务角色仍需知识库成员授权；Administrator 管理授权但不自动读取资料。
- 评论不可编辑，不提供删除；需要更正时追加评论。工单终态不可重开，创建新单并在描述中引用旧单。
- 文档软归档；默认新检索仅使用当前 READY 版本，历史版本仅供经鉴权的引用追溯。
- 管理后台包含账号/角色、部门、知识库成员与审计列表，不增加工作流设计器。
- 不实现跨组织、社区、即时聊天、会议、OCR、PPT/Excel、Marketplace、自动编程、复杂 BPMN 或多 Agent。

## 非功能预算与验收语义

开发环境建议 4 CPU / 8 GB RAM，真实本地 embedding 额外占用内存。文件上限 20 MiB、PDF 300 页、解压内容 100 MiB；每用户上传 10 次/小时、AI 问答 20 次/分钟、登录每账号与 IP 5 次/分钟，均可配置。问答请求预算 35 秒，解析单次任务预算 120 秒。Phase 7 用实际机器测量 p50/p95，不能把预算当结果。

AI 不可用不阻塞工单或文档元数据查询。Redis 不可用时需会话校验的请求返回 503；服务内部凭据与存活检查不依赖 Redis。知识索引失败保持旧 READY 版本可用。所有关键写入审计失败应回滚业务事务。

冻结表示首版边界与取舍已经决定，不表示实现完成。修改范围必须同步 ADR、契约与验收用例。
